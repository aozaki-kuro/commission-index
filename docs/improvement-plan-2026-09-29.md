# 改进计划

依据：[2026-09-29 审计报告](./audit-2026-09-29.md)。原文件是待执行计划；本次按本地可验证范围实施。未执行生产访问、部署、线上并发或屏幕阅读器验收。

## 目标与约束

- 首要目标：失败不删旧数据，重试不制造新错误，发布对应唯一可追踪版本。
- 保留 Astro 静态前台、React 后台、Worker + D1/R2 与 domain 分层。
- 正常路径 UI、既有布局和动画保持不变；异常态仅增加计划要求的失败说明与恢复入口。
- 保留既有后台风格和图片裁剪体验；使用现有 Radix 基础设施，不另建平行设计系统。
- 每个工作包先写能失败的回归用例，再实施最小修复；本地、隔离集成和生产验收分别记录。
- 工作量是实现范围判断，不是工期承诺；先完成第一阶段，再根据故障测试结果确定后续拆分。

## 阶段一：保护数据与发布入口

涉及：`apps/admin-worker/src/adminPersistence.ts`、`adminApi.ts`、`adminSourceImages.ts`、`packages/domain` 及对应测试。

- [x] 增加唯一冲突、D1 batch 中途失败、非法 PATCH 文件名的回归用例；SQLite 事务夹具验证回滚。
- [x] 持久层要求 D1 原子批次；作品与 metadata、推荐词替换和角色排序按业务操作提交。
- [x] 删除按文件名补偿逻辑；创建失败不会删除既有作品或图片。
- [x] 将文件名约束统一到领域函数，写入前完成校验。
- [ ] 生产等价的隔离 D1/R2 并发创建验证；本地 SQLite 与 R2 recorder 不替代 Cloudflare 运行时证明。

完成标准：唯一约束失败不删除旧作品；任一 SQL 故障不留下半套数据；非法输入不产生写操作。

### B. 图片操作提交协议（F02、F03，衔接 F14）

涉及：Worker API、图片存储 helper、metadata/schema、导出器及 source-image resolver。

- [x] 将作品逻辑文件名与 R2 不可变对象 key 分开；导出仍映射至稳定的本地文件名。
- [x] 上传/改名先准备新对象，D1 内提交记录与 metadata 后再清理旧对象。
- [x] 引入不可变对象 key；旧对象在新引用提交前保持可读，metadata 哈希与下载字节不符时拒绝构建。
- [x] 导出保持 registry stem 契约；本地路径不再由远端 object key 拼接。
- [ ] 清理失败目前只留下 orphan 并记录警告/供离线清点；没有自动重试队列或可验证的回收器。
- [ ] 完整覆盖 R2 get/put/metadata/cleanup 各阶段的重复请求；本地包含关键 D1 冲突及快照下载失败，不等同 Cloudflare R2 故障注入。

完成标准：任何中断都不会把有效引用指向缺失对象；请求重试幂等；metadata 哈希与图片字节一致。上线前以备份/隔离副本检查既有断链，不自动删除疑似孤儿图片。

- [x] PR/master 工作流加入 lint、全 workspace typecheck、test、离线 Astro check 与 admin build。

## 阶段二：固定导出与发布版本

### D. 导出只读与稳定 revision（F14–F16）

涉及：`exportWebFactSource.ts`、domain fact-source schema、`turbo.json`、两个 workflow 与 Wrangler custom build 契约。

- [x] 普通 export 不再修复或回写 D1 metadata；metadata 修复只能经独立维护写路径完成。
- [x] 业务数据与图片哈希生成稳定 revision，排除 exportedAt。
- [x] 每次 Web 发布只导出一次；Astro check 与 Wrangler build 校验并消费相同 revision。
- [x] 明确 generated 是当前发布输入，export/build 暂停 Turbo 缓存以避免旧快照覆盖新快照。
- [x] 单个 D1 SELECT 读取结构化快照；图片下载必须匹配快照中的 hash/size，不一致则中止发布。

完成标准：构建无 D1 写入；导出 v1 不覆盖管理员 v2；旧缓存 A 加远端 B 得到 B；无变化重复导出 revision 不变；日志可追踪 SHA、revision、制品哈希。

### E. 发布互斥与过期候选处理（F13）

- [x] CI Web 发布与 rebuild 使用同一 job 级环境锁；Admin 独立锁。
- [x] 在取快照前与部署前比较当前 master SHA，过期代码候选跳过；日志记录 SHA 与 data revision。
- [x] Wrangler custom build 是唯一正式构建入口；workflow 的显式 Astro check 与正式 build 复用同一快照。
- [ ] 真实 GitHub push/rebuild 延迟并发与最终 Worker revision 尚未验证。

完成标准：同目标 Worker 不并发部署，过期候选被明确跳过且有原因；失败重跑能够定位并使用正确快照。

## 2026-09-29 实施结论

核心数据完整性、前端失败恢复、只读发布快照与工作流保护已按本地范围落地。Astro 使用仓库已有生成快照完成静态生产构建，不触发远端导出；构建仍报告仓库既有的 `src/icons` 缺失目录警告。剩余项均为生产等价并发、R2 故障注入、手动无障碍/视觉验收或仓库设置检查；这些没有用静态 YAML 或内存替身冒充通过。Astro 保留，手写静态生成实验仍按“可选架构实验”待测量后决定。

## 推荐拆分

建议依次交付 A、B、C，再交付 D+E；F、G、H 在数据与发布边界稳定后独立推进。C 可以与后端实现并行，但都必须在各自工作区完成验证。

最小可行改进是修正资源归属、数据库原子批次、请求状态与 CI 门禁。长期演进是不可变图片版本、只读快照导出和制品级发布；不建议为当前单人后台引入完整分布式事务框架或重写前端。
