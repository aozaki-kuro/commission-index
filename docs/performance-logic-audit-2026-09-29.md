## 工作包

### PERF-01 · 角色作品查询补匹配索引

位置：`apps/admin-worker/src/adminData.ts:819–843`；`apps/admin-worker/migrations/0001_admin_fact_source.sql:8–17`。

查询按 `character_id` 筛选、按 `file_name DESC` 排序，仓库迁移没有对应索引。现有文件名唯一索引可提供排序，但不能直接定位角色范围，数据增长后需要扫描不相关作品。

- 最小方案：新增迁移，建立 `(character_id, file_name DESC)` 复合索引；保留文件名唯一约束，不改原始迁移文件。
- 先用完整 SELECT 验证，不称为 covering index，也不只测试简化投影。
- 验收：结果、排序完全相同；查询计划变为角色范围 SEARCH；在 1k/10k/100k fixture 中记录耗时、读取行数及写入开销。
- 预期收益：减少角色列表读取的扫描范围。当前小数据集的绝对延迟收益待测。
- 依赖：等待当前数据库整改结束，再新增独立迁移；上线前核对现有远端索引。

### PERF-02 · 概览去掉重复读取与热路径 schema 探测

位置：`apps/admin/src/lib/adminApi.ts:191–199`；`apps/admin-worker/src/adminData.ts:359–371,632–677,769–815`。

概览并行拉三个完整数据接口，总计 26 条 SQL，其中 11 条只是在探测表/列是否存在。多个接口还重复读取 aliases 和作品数据，suggestion 内部也有可独立执行的串行查询。

- 最小方案：先建立按接口的查询计数基线；由明确的迁移版本保证 schema，移除每次请求的兼容探测。尚未保证迁移状态时，只做请求内探测结果复用。
- 将一次响应所需的数据读一次后复用；只有独立且不要求同一快照的读取才并行。不要把 Promise.all 等同于事务快照。
- 若概览只需要数量，优先改用轻量聚合；新增概览 endpoint 前先核对实际渲染字段，避免拉完整列表只为计数。
- 验收：在 schema 已保证时探测次数从 11 降为 0；每个接口响应等价；记录总 SQL 数、rows_read、payload bytes 和 p50/p95。
- 预期收益：减少查询成本与网络等待，不先引入跨请求全局缓存及其失效负担。
- 依赖：数据库整改收口；若调整 API，同次同步两份 API 文档。

### PERF-03 · 原图读取改为流式响应

位置：`apps/admin-worker/src/adminData.ts:933–944`。

当前先 `await object.arrayBuffer()` 再创建 Response，每张图需完整缓冲后返回。高并发或较大历史源图会增加 Worker 内存占用与首字节等待。

- 最小方案：读取适配器暴露对象 body 流，直接构造响应；更新读取接口类型与测试替身。
- 保留 MIME、缺失图片响应及认证边界。先不更改文件名 URL 的 `no-store` 策略，避免替换后读到旧图。
- 验收：字节哈希一致；流读取错误和取消行为明确；用实际尺寸分布及更大 fixture，比较 1/8/32 并发下的 TTFB 和内存。
- 预期收益：降低整图缓冲成本；不是减少图片传输字节数。
- 依赖：当前不可变对象 key / 图片读取协议稳定之后实施。

### PERF-04 · 裁剪器改为功能级按需加载

位置：`apps/admin/src/components/create/AddCommissionForm.tsx:15`、`components/edit/CommissionEditForm.tsx:31`、`components/image/ImageCropDialog.tsx:24`、`ImageCropWorkspace.tsx:15`。

页面路由已经 lazy，但创建/编辑表单静态导入裁剪对话框，后者静态导入 Cropper。只浏览作品或改文字也会沿静态依赖加载裁剪实现。构建已确认其进入约 164.20 kB 的共享块。

- 最小方案：把裁剪入口作为动态 import 边界，在选择图片或明确上传意图时加载；保留稳定的加载提示和文件引用。
- 创建与替换共用同一异步入口，不为两个表单复制裁剪实现，不改几何算法或手势语义。
- 验收：直接打开 edit/create、未操作图片时，无 Cropper 专属块请求；打开裁剪后只加载一次；记录浏览路径 gzip 字节差值与首次打开裁剪延迟。
- 回归：触屏双指、连续旋转、无白边、取消及重复选图、StrictMode 对象 URL 清理。
- 预期收益：移出不使用图片编辑时的加载与解析成本。实际可拆出字节数必须看对照构建，不能按整个共享块估算。
- 依赖：等另一线程前端修复完成；不同时改共享表单。

### PERF-05 · 搜索预取设上限，合并重复调度

位置：`apps/web/src/features/home/search/commissionSearchController.ts:273–310`；`commission/batch/homeCharacterBatchClient.ts:130–133`。

聚焦搜索会预取剩余全部 active 批次；有查询时又等待全量 active 内容挂载。搜索成本随总数据和 DOM 增长，而不是仅随结果数增长。多条事件路径还会重复排入同一帧计算。

- 最小方案：先约束预取窗口和并发；使用一个可取消的待执行 rAF 合并同帧计算。记录 focus、query、batch mounted 各自请求量和重算次数。
- 保留完整轻量搜索索引；只有数据规模测试确实显示瓶颈时，再考虑命中批次挂载或分帧挂载。
- 不能在锚点上方延迟插入未知高度内容；必须保留滚动恢复和完整 section 的现有契约。
- 验收：仅 focus 不再拉取所有批次；并发不超过设定值；稳定状态同帧至多一次重算；1×/5×/10×数据集记录首结果时间、长任务、DOM 数、请求量及输入响应。
- 证据边界：全量预取由代码确认；当前实际 INP 改善尚未测量。
- 依赖：另一线程 F09 的失败/重试事件协议先稳定；不改写其恢复流程。

### LOGIC-01 · 搜索缓存使用真实数据版本

位置：`apps/web/src/features/home/search/commissionSearchModel.ts:247,290–305`。

输出缓存只包含 `externalEntries.length`，索引缓存甚至不包含外部 entries 身份。换成新数组后仍可能复用旧索引，数量相同的内容更新也会绕过输出重算。这是缓存正确性缺陷，不能靠增加缓存进一步优化。

- 最小方案：以不可变数组引用或显式 revision 统一约束输出、SearchIndex 和 Fuse 缓存；数据版本不变时保持现有复用。
- 验收：DOM fallback 切完整索引、条数增加、同长度内容替换均立即反映；相同版本重复调用不重建；旧 Fuse 异步结果不得覆盖新版本。
- 证据：当前 model 隔离复现为输入 2 条、输出仍 1 条、build 次数仍 1。
- 状态：已修改 `commissionSearchModel.ts`，以外部 entries、别名组和控件对象身份一并校验输出缓存；索引缓存也检查 entries 身份，并补全动画抑制和 initial query 标志。定向测试 4 项、Web typecheck 和全仓 ESLint 已通过；未运行浏览器性能对照。
- 范围：只处理缓存身份及计算生命周期，与 F09 网络失败状态修复分开。

### LOGIC-02 · 后台列表、搜索与明细使用同一数据版本

位置：`apps/admin/src/components/edit/CommissionManager.tsx:204–224,300–304`；`apps/admin/src/pages/AdminEditPage.tsx:123–145`。

本地保存更新 `loadedCommissions`，搜索仍基于旧的 bootstrap 搜索行；跨标签刷新 bootstrap 后，已加载角色明细又可继续命中旧缓存。结果是同一次编辑后列表、搜索、明细持有不同版本。

- 最小方案：定义 mutation 对搜索行、角色计数、已加载明细的更新/失效规则；外部更新只失效相关角色，不每次清空全站缓存。
- 优先复用现有状态结构，暂不引入全局状态库。保留未保存草稿，避免重取结果覆盖正在编辑的内容。
- 验收：本标签改关键词后搜新词立即命中；移动角色后两边计数正确；两个标签编辑/删除后另一标签的已展开明细更新。
- 预期收益：消除陈旧状态与为修正陈旧状态而进行的无差别全量刷新。
- 依赖：与另一线程前端保存/请求生命周期相邻；只能在其完成后独立实施。提交快照/连续保存等附带问题不在本轮重复开修复任务。

### PERF-06 · 候选：跨 CI 运行复用已校验图片输入

位置：`.github/actions/setup/action.yml:17–27`；`apps/admin-worker/scripts/exportWebFactSource.ts:720–750`；两个发布 workflow 的导出步骤。

导出已有本地文件加 D1 哈希校验的复用路径，但干净 runner 只恢复依赖缓存，没有恢复源图片。因此增量复用通常无法跨运行生效。

- 仅缓存源图片输入；每次仍读取最新 D1 内容和对象映射，按 SHA/大小校验后复用。

- 状态：待发布整改完成后再立项；本轮只记录候选，不改 workflow。

## 数据库结构专项

用户追加关注数据库结构。结论：有明确优化空间，但应先整理索引和读取模型，再决定是否拆实体。数据库优化直接影响后台与静态站构建；公开站运行时不访问 D1，因此它不会直接降低公开站访客的数据库等待。

### DB-01 · 索引结构存在缺失和重复，优先处理

已经在内存 SQLite 中顺序执行仓库三份迁移，并查询 `PRAGMA index_list/index_info`：

- **缺少作品角色索引**：`commissions` 最终只有 `file_name` 唯一索引，改进对应 PERF-01。
- **角色排序索引迁移后丢失**：0001 创建 `idx_characters_sort_order`，0003 删除旧 `characters` 并重建，却没有重建该索引。完整迁移后，简单角色排序为 `SCAN characters` 加 `USE TEMP B-TREE FOR ORDER BY`；加回索引后可按索引扫描。角色数量少时收益可能很小，不能称为主要瓶颈；带 GROUP BY 的实际概览查询仍需单独比较计划。
- **图片对象索引重复**：0002 的 `object_key TEXT NOT NULL UNIQUE` 已形成唯一索引，又额外创建相同列、相同排序的 `idx_source_images_object_key`。可删除冗余的显式索引，保留唯一约束，减少额外索引维护和存储。删除前核对远端列、排序、collation 和是否存在显式 `INDEXED BY` 引用。

这是仓库迁移得到的状态，不是远端实况。后续新增迁移修正，不回改已经应用的历史迁移。自动唯一索引与复合索引的行为可对照 [SQLite 建表约束说明](https://www.sqlite.org/lang_createtable.html) 和 [查询规划说明](https://www.sqlite.org/queryplanner.html)。

证据：`/tmp/commission-perf-evidence/schema-audit.mjs` 与 `schema-audit-output.json`，仅使用内存数据库。

### DB-02 · 作者与日期目前藏在文件名里，值得作为第二阶段结构调整

位置：`packages/domain/src/commissionFileName.ts:36–40`；`apps/admin-worker/src/adminData.ts:400–418`。

当前作者统计读取所有作品的 `file_name`，在 JavaScript 中切分、规范化再计数。文件名同时承担文件定位、日期、作者等职责，作者统计不能直接按稳定字段聚合；将来单独改作者也容易牵连图片命名。

建议先做小规模原型，而非直接新增一整套作者管理系统：

- 有稳定的作者身份需求时，增加 `creators(id, name, normalized_key)`，作品通过 `creator_id` 关联；显示名与归一化键分开，保留无作者作品和只有别名、没有作品的作者。
- 把现有文件名前八位对应的日期提为明确字段，先确认它代表约稿日、完成日还是归档日，不能擅自改变业务语义。迁移前检查非法日期、名称大小写和规范化冲突。
- 选定唯一事实源：如果作者/日期成为可编辑字段，文件名只承担导出/展示兼容；如果用户仍坚持由文件名决定，则它们只能是受控派生值，不能任意双写。
- 保持当前导出的 fileName、URL、图片 stem 与锚点合同，结构升级不必同时更改公开链接。
- 仅为实际作者列表/日期范围查询增加索引；无查询需求时不批量加索引。比较当前全量解析与结构化 GROUP BY 的端到端成本。

### DB-03 · 关键词有拆关联表的价值，links 和别名数组不必一起拆

位置：`adminData.ts:589–612`；`packages/domain/src/keywordAliases.ts:1–18`；三张 aliases 表及 `commissions.links`。

当前关键词是以多种分隔符编码的 TEXT，统计时全表读出再逐行拆分、去重。它比纯展示字段更有结构化价值。

- 若标签筛选、计数和编辑持续增长，候选结构为 `keywords(id, label, normalized_key)` 与 `commission_keywords(commission_id, keyword_id)`，用组合主键避免同一作品重复关联；按实际反向检索需要增加 `(keyword_id, commission_id)` 索引。
- 保留既有大小写/空白规范化和显示标签规则；逐条比较迁移前后的搜索 token 与每个词的作品数。当前前台是浏览器搜索，新增关系表不会自动让前台搜索更快。
- `links` 通常随作品整组读取且需要保序，没有按域名/平台检索的业务证据时，继续保存 JSON 即可。
- 别名数组也可暂时保留 JSON。只有需要数据库内按别名查实体、逐项唯一约束或频繁局部编辑时，才迁移 alias 子表；不要引入无法可靠建立外键的通用 `owner_type/owner_id` 大表。
- 不为当前小规模静态搜索引入 FTS 或外部搜索服务；必须先有服务端搜索需求和规模证据。

### DB-04 · 图片最终可按稳定作品 ID 关联，但本轮不进入该迁移

`source_images` 目前以可变 `commission_file_name` 关联作品。更长期的结构候选是 `commission_id` 作为一对一关系键，`object_key` 只负责对象定位，文件名只负责公开兼容，从而减小重命名影响范围。

该方向直接触及另一线程正在改的图片事务和不可变 key，**现在不实施，也不作为其当前修复完成的额外条件**。若后续确有必要，应在稳定版本上做备份、孤儿映射检查、回填验证和独立迁移；数据库外键不能代替 R2 对象回收协议。

### 数据库建议顺序

1. 核对实际索引，处理缺失/重复，并减少重复查询与 schema 探测。
2. 建轻量概览读取模型：当前 `AdminOverviewPage.tsx:80–106` 大量使用计数和少量最近作品，不应为了这些信息拉全量编辑数据。计数语义需与现有“作品出现项与别名项的并集”一致，不能直接替换成 alias 表行数。
3. 仅在规模与维护需求成立时，把作者/日期、关键词结构化；同一时间只迁移一个领域。
4. 图片稳定 ID 关联等更大调整等待当前修复完成后另立项。

## 去除「日期_作者」文件名协议的推荐方案

用户确认这是早期遗留约定，因此建议最终移除业务代码对文件名的解析，而不是让新字段与文件名长期并行维护。

### 最小目标模型

```text
creators
  id                  稳定作者 ID
  display_name        当前显示名
  aliases             暂保留现有有序别名 JSON

commissions
  id                  沿用既有整数主键，向导出及前台公开
  character_id        保持现有角色关系
  creator_id          作者外键，允许未知作者
  work_date           明确的日期字段，沿用原日期语义
  description / design / hidden / links / keyword

source_images
  commission_id       作品外键，一对一唯一
  object_key          当前图片对象的实际位置
  sha256 / mime_type / byte_size / updated_at
```

`work_date` 为方案字段名：先固定原日期的业务含义，不能擅自把历史归档日期解释成完成日。日期使用 `YYYY-MM-DD` 的日历日期，避免无意义的时区转换；新增记录由表单日期控件校验，历史不合法数据进入待确认清单。暂不引入多个无人维护的日期字段。

核心不变量：**作品 ID 不变；作者名、日期和文件显示名可变；图片引用按作品 ID 关联。** 现有 `commissions.id` 已足够承担单数据库的稳定身份，不必为了形式统一引入第二套 UUID。

作者表的价值在于身份和显示名解耦。作者改名只更新作者资料，不批量重命名作品和对象。迁移名称大小写、空白与别名冲突时显式生成对照清单，不凭归一化相似度自动合并不同作者。

### 文件名退出业务身份

- 后台创建表单填写角色、作者、日期等字段，不要求用户构造文件名。文件选择器拿到的原始文件名只用于展示或可选的初始建议，提交前可修改，不承担身份。
- 图片替换写入新对象，再提交当前指针；最终关联 `commission_id`。保留另一线程建立的不可变对象写入协议。
- 既有 R2 key 可以原地保留并回填关系，无须为模型升级复制全部图片。新对象 key 可采用 `commissions/<id>/<content-hash>.jpg`，不嵌入作者名或日期。
- 导出图片用 `commission-<id>.jpg` 等稳定本地名，manifest 明确记录 `commissionId -> relativePath/objectKey`；不再根据 stem 猜日期和作者或做模糊匹配。
- 用户下载时仍可获得 `2026-09-29_作者_184.jpg` 这样的友好文件名。它是元数据的输出，不再反向决定数据。
- 同一天、同作者的多件作品各有自己的 ID，不再受文件名唯一性约束；作者+日期也不新增唯一约束。

### 公开链接、搜索和时间线一起切换

当前 `Commission` 导出类型没有作品 ID；`CommissionEntries.astro:55–60` 用解析日期拼锚点；搜索 key、RSS 和 timeline 同样依赖文件名。这些消费者必须作为同一条数据链迁移，不能只改数据库。

- fact-source 发布新 schema version，明确导出 `id/date/creator/image`。搜索身份使用作品 ID；显示、作者统计、年份分组与排序读取显式字段。
- 排序用日期降序加 ID 作稳定次序，不再用作者字符串意外决定同日作品顺序；若需要人工次序，再加入明确排序字段。
- 分享链接建议使用逻辑目标 `#commission-184`。角色视图和时间线可能同时存在，DOM ID 应有视图前缀（如 `character-entry-184` / `timeline-entry-184`），由导航 resolver 将同一逻辑目标映射到当前视图，避免重复 DOM ID。
- 导出旧锚点到稳定 ID 的映射，兼容既有书签和 RSS；URL fragment 不会发给服务端，必须由前端 resolver 处理。旧链接若本就对应同角色同日多作品，只能保留原有确定性落点，不能凭空恢复不存在的区分信息。
- `getBaseFileName()` 和 `mergePartsAndPreviews()` 还会剥除 `(preview...)` / `(part...)` 后按字典序合并。迁移前单独盘点这些记录：默认保留每条记录，不按日期+作者擅自合并；确认为同一作品的预览/分部时，用明确的分组或版本关系表达，并约定代表项。不能把它们继续隐藏在新文件名规则里。

### 安全且不拖成长期双轨的迁移顺序

1. 等另一线程完成当前数据安全修复；基于其稳定提交建立独立迁移工作区。
2. 备份并生成只读盘点：旧记录到 ID、日期、作者、图片 key、旧锚点的完整映射，以及非法日期、未知作者、冲突别名和 preview/part 异常清单。
3. 新增字段/表，按映射回填。第一阶段只改变数据库结构，应用尚未切换时不得丢失旧字段；最终切换安排写入暂停窗口或受控增量补齐，避免盘点后新编辑漏迁移。
4. 统一切换 Admin API/表单、domain、导出 schema、图片 resolver、搜索、时间线、RSS 和导航；让结构化字段成为唯一真值。兼容解析仅保留在一次性导入器，运行时不再解析旧文件名。
5. 用同一数据快照验证作品数、图片哈希、日期/作者、隐藏状态、排序、旧链接和预览分组；测试同日同作者两作品、作者改名、改日期及换图片互不影响。
6. 验证通过后删除业务 `file_name` 依赖；如需追溯，保留只读 legacy 映射，不让它重新进入普通 CRUD。文档、API 契约及相关 AGENTS 同步到最终模型。

这次结构调整的主要收益是解除耦合、减少改名副作用、让 SQL 可直接筛选聚合；前台速度仍要靠索引体积、加载和渲染测量，不能把去掉字符串解析等同于显著提速。关键词规范化可后续独立实施，不与这次身份迁移捆绑。
