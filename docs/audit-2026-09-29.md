## 设计反模式结论

本次不对整个产品给出“像 AI 生成”或视觉合格的结论：完整页面的视觉证据不足。已有 `.impeccable.md` 明确要求克制、中性、精确的私人编辑工具，现有组件与字体规范值得保留，没有证据支持整站重做。

实际需要优先改善的是交互可信度：保存是否真的完成、失败后能否重试、模态窗口是否真正隔离背景、缓存是否向用户隐瞒更新失败。对应 F07–F11。这些比替换配色、圆角或布局更直接影响维护效率。

## 高优先级发现

### F01 · P1 · 创建失败回滚没有资源归属判断

- **位置：** `apps/admin-worker/src/adminApi.ts:372–384`；`adminPersistence.ts:493–495`。
- **触发：** 已有作品的 D1 记录存在、R2 图片缺失；同名创建先成功上传，再因唯一约束导致 INSERT 失败。
- **缺陷：** catch 无论 INSERT 是否成功，都按文件名删除作品与元数据，可能删掉旧记录。并发同名创建也需要纳入测试。
- **证据：** 内存故障注入返回 400 / `UNIQUE constraint failed: commissions.file_name`，同时执行了 `DELETE FROM commissions WHERE file_name = ?`。
- **改进：** 仅清理本次拥有的资源，以创建返回 ID/操作标识判定归属；作品与图片元数据在同一个 D1 原子批次提交。对象写入也必须处理同名并发，不能只用先读再写。
- **验收：** INSERT 未成功时原记录、原元数据、其他请求的对象完全不变。

### F02 · P1 · 重命名提前提交 D1，失败后重试跳过修复

- **位置：** `apps/admin-worker/src/adminApi.ts:400–429`；`adminPersistence.ts:445–472`。
- **触发：** 文件名变更后，R2 读取/复制或新元数据写入失败。
- **缺陷：** 先更改作品文件名并删除旧 metadata，再迁移 R2；重试时文件名已经相等，跳过迁移。缺失旧元数据/对象或 IMAGES 时还有静默成功路径。
- **证据：** 注入 put 失败后，首次 400，但作品已经改成新名且 metadata 为 null；重试 200，累计 put 仍为 1。
- **改进：** 先验证所有依赖并准备新对象，再原子切换作品及 metadata，最后回收旧对象；中断点可安全重试。
- **验收：** 每个失败点保持旧版本可读或明确的可恢复状态，重试不能仅返回成功而保留断链。

### F03 · P1 · 替换图片失败留下新对象与旧哈希

- **位置：** `apps/admin-worker/src/adminApi.ts:458–464`；`adminSourceImages.ts:189–211`；`scripts/exportWebFactSource.ts:748–758`。
- **触发：** 覆写 R2 成功后，metadata 写入失败。
- **影响：** 接口报错但图片已变；D1 旧哈希仍可让导出复用本地旧图片，后台与公开构建可能持续不一致。
- **证据：** 故障注入得到 400、R2 为新字节、metadata 保持旧哈希；旧构建复用是代码推导，未运行生产构建。
- **改进：** 新内容写不可变对象 key，D1 成功切换指针后再清理旧 key。迁移时同步调整导出文件名映射，不能让对象 key 直接破坏现有本地文件布局。
- **验收：** metadata 写入失败时旧图片仍完整；成功后 manifest 哈希和实际字节一致。

### F12 · P1 · PR 没有服务端完整质量门禁

- **位置：** `.github/workflows/ci.yml:40–41,53–57,87–91`；`.pre-commit-config.yaml:26–51`。
- **缺陷：** PR 只执行 admin build；lint、workspace typecheck、单元测试仅依赖本地 pre-push hook。Web check 只在 master job 执行。
- **影响：** 跳过本地 hook 或网页提交后，Worker 类型错误、单测失败和前台问题仍可能进入发布链。
- **证据：** 当前 workflow 静态确认；本轮本地检查通过不能替代远端持续门禁。
- **改进：** PR/master 都执行独立 validate job，部署依赖它成功；Web PR 使用固定脱敏 fixture，避免依赖生产凭证。
- **验收：** 分别引入失败单测、Worker TS 错误和 Astro 错误，均被相应 CI job 阻止。

### F13 · P1 · 两个发布入口缺少共享互斥与过期版本检查

- **位置：** `.github/workflows/ci.yml:10–12,96–100`；`rebuild.yml:8–10,79–88`。
- **缺陷：** push 使用 workflow/ref 分组，数据重建使用 `release-master`，两者可同时发布同一 Web Worker。
- **影响：** 完成先后可能使较旧代码或数据快照覆盖新发布。单个 group 的 `cancel-in-progress: false` 不提供跨 workflow 互斥。
- **证据：** 配置可达的竞争条件；未触发生产并发部署。
- **改进：** Web 发布共享环境级锁，并比较代码 SHA、数据 revision，拒绝过期候选。仅加锁不能保证候选版本的新旧顺序。
- **验收：** 并发触发 push 与数据重建，延迟旧候选，最终线上仍为最新允许发布的版本。

### F14 · P1 · 构建导出会无条件写回生产元数据

- **位置：** `apps/admin-worker/scripts/exportWebFactSource.ts:624–629,784–791,954–984`。
- **缺陷：** 下载内容与起始 metadata 不一致时，导出会无版本条件 upsert D1；构建消费者同时成为生产写入者。
- **触发交错：** 导出读 v0 → 下载 v1 并排队回填 → 管理员完成 v2 上传与 metadata → 导出将 metadata 覆盖为 v1。
- **影响：** 新 metadata 被旧状态覆盖，后续缓存复用可能进一步放大不一致。
- **证据：** 静态写入链和并发时序推导；需要 metadata 缺失/不一致的分支，不能描述为每次导出都会发生。
- **改进：** 普通导出只读；metadata 修复拆成明确维护操作，并用旧 revision/hash 的条件更新。构建绑定稳定快照。
- **验收：** 注入上述交错，导出绝不覆盖 v2；只读导出不得执行任何 D1 mutation。

## 中优先级发现

### F04 · P2 · 多语句 D1 操作缺少原子提交

- **位置：** `apps/admin-worker/src/adminPersistence.ts:709–724`；角色排序同类模式见 `302–329`。
- 推荐关键词先 DELETE 再 INSERT，第二步失败会清空原配置。内存注入已复现 `['old'] → []`。
- **改进与验收：** 用单次原子批次提交一个业务操作；在每条写语句故障时，数据保持全部旧值或全部新值。排序同时检查 ID 唯一、完整与合法。

### F05 · P2 · PATCH 文件名与创建/读取校验不一致

- **位置：** `apps/admin-worker/src/adminApi.ts:220–229,575–585`；严格规则在 `adminSourceImages.ts:86–109`。
- 更新只检查非空，`../invalid` 等值可进入 D1，却不满足图片读取及导出契约。内存调用已确认该值可被持久化。
- **改进与验收：** 领域层统一创建、更新、读取规则；路径字符、扩展名、控制字符在任何写入前被拒绝。此处是数据契约缺陷，不是已证明的任意文件执行漏洞。

### F06 · P2 · 开发 StrictMode 使排序保存队列永久停用

- **位置：** `apps/admin/src/hooks/useCommissionManager.ts:305–314,359–364`；`src/main.tsx:14–17`。
- render 创建 ref 队列，effect cleanup dispose，下一次 setup 不重建。开发环境 effect replay 后排序只更新本地 UI。
- **证据：** 当前源函数转译执行：正常 enqueue 保存次数 1，dispose 后再次 enqueue 为 0。未执行完整 React 挂载复现；影响限定开发模式，不声称生产必现。[React StrictMode 文档](https://react.dev/reference/react/StrictMode)确认开发时额外 effect 生命周期。
- **改进与验收：** 在 effect setup 创建实例、cleanup 清理对应实例；StrictMode 挂载后排序确实提交，真实卸载后不再提交。

### F07 · P2 · 删除 pending 没有覆盖实际网络请求

- **位置：** `apps/admin/src/hooks/useCommissionManager.ts:509–535`；`CharacterDeleteDialog.tsx:36–39,57–59,131–136`。
- transition 回调启动 Promise 却不返回/等待；按钮、Escape、遮罩仅依赖 `isDeletePending`，可能重复提交，旧请求 finally 还能关闭后来打开的确认框。
- **证据：** 静态 Promise/状态链确认，未执行真实删除；异步 action 行为参考 [React useTransition](https://react.dev/reference/react/useTransition)。
- **改进与验收：** 请求级防重入与异步状态覆盖完整请求，用请求身份隔离结束回调；延迟 Promise 下连续点击只提交一次。

### F08 · P2 · 删除模态缺少键盘焦点隔离

- **位置：** `apps/admin/src/components/edit/CharacterDeleteDialog.tsx:23–44,63–67`。
- 只有打开时聚焦 Delete 与 Escape 处理，没有焦点循环、背景 inert、关闭后恢复触发点。`aria-modal` 本身不会实现行为。
- **影响：** Tab 可进入遮罩后控件；默认聚焦不可逆动作也增加误操作机会。完整组件静态确认，未做读屏实测。
- **改进与验收：** 复用现有 Radix Dialog/适当的 AlertDialog 模式，初始聚焦 Cancel；Tab/Shift+Tab 保持在窗口内，关闭后回到触发控件。参考 [WAI-ARIA Alert Dialog 模式](https://www.w3.org/WAI/ARIA/apg/patterns/alertdialog/)。不据此声称已完成 WCAG 合规检测。

### F09 · P2 · 公开搜索加载失败后没有释放请求标记

- **位置：** `apps/web/src/features/home/search/commissionSearchController.ts:303–329`；`commission/loader/activeCharactersLoader.ts:257–260`。
- controller 先设置 requested 标记，loader 失败仅记录错误，不通知释放；activeLoaded 仍 false 时筛选持续暂停，继续输入不会重新发起同一加载。
- **证据：** 静态状态链；其他视口加载/视图切换可能恢复，不能声称永远只能刷新。
- **改进与验收：** 将标记收口为真实 in-flight 状态，失败可重试并展示反馈；先返回一次 500 再恢复，继续搜索能自动或显式重试并正确筛选。

### F10 · P2 · 路由代码块加载失败没有局部恢复界面

- **位置：** `apps/admin/src/App.tsx:8–13,206–208`；`main.tsx:14–17`。
- React.lazy 页面外只有无 fallback 的 Suspense，未发现应用错误边界。首次等待可为空白；chunk 拒绝时缺少应用内恢复路径。
- **证据：** 静态检查，未模拟线上旧 chunk 404。
- **改进与验收：** 路由级错误边界、稳定占位与重新加载入口；处理 lazy 对失败 Promise 的缓存，不能只清除错误 state。断网或 chunk 404 时外壳保留，恢复入口可用。

### F11 · P2 · 有缓存时刷新错误被界面隐藏

- **位置：** `apps/admin/src/pages/AdminEditPage.tsx:150–162,257–265`。
- fetch 失败虽记录错误，但 payload 非空分支直接返回 dashboard，不显示失败或 Retry。用户看到旧内容，却不知道刷新没有成功。
- **证据：** 静态分支确认。
- **改进与验收：** 保留旧内容同时显示非阻塞“刷新失败/可能过时”和重试按钮；缓存命中后请求 reject 必须出现提示。

### F15 · P2 · 缓存版本包含导出时间

- **位置：** `.github/workflows/rebuild.yml:60–66`；`apps/admin-worker/scripts/exportWebFactSource.ts:648–660`。
- 对完整 JSON 哈希，而每次导出都写新的 exportedAt；内容未变也改变 cache token，失去跨运行复用收益。
- **证据：** 静态确定；属于效率缺陷，不是已发生的数据回退。
- **改进与验收：** 对稳定排序的业务内容及图片哈希计算 revision，时间单独记录；两次无内容变化导出 revision 相同，改描述或图片则不同。

### F16 · P2 · 导出、缓存恢复与发布没有绑定同一快照

- **位置：** `.github/workflows/ci.yml:81–100`；`turbo.json:18–27`；`apps/web/wrangler.jsonc:11–12`。
- CI 先直接 export，build 又依赖可缓存 export task；CI 未设置远端数据 token。若命中旧 task 输出，generated 可能被缓存覆盖；未命中则重复导出。deploy 再通过 Wrangler custom build 进入构建流程。
- **证据：** 配置可达的条件风险；没有检查线上缓存是否具备触发条件，不能断言已经发布旧内容。
- **改进与验收：** 一次导出确定 revision，检查、构建、部署消费同一快照/制品；准备旧缓存 A 与新数据 B，最终发布必须为 B，并记录导出实际调用次数。

## 系统性原因与设计建议

1. **资源归属与提交点不明确。** 图片上传、作品记录和 metadata 各自提交，再靠 catch 补偿。D1 原子性解决数据库内部问题；跨 D1/R2 则需要“准备对象 → 原子切换引用 → 延迟清理”，不能把两个远程系统假设成一个事务。
2. **请求已发起被当成请求已完成。** 搜索加载、删除 transition、排序队列都缺少可靠的生命周期闭环。优先使用已有组件和小型请求状态，不必引入大型全局状态框架。
3. **发布存在多个事实源。** 远程数据、generated、Turbo 输出和导出修复写回都可改变待发布内容。用明确 revision 贯穿链路。
4. **测试主要覆盖成功路径和纯函数。** 当前 212 个测试全通过仍遗漏写入中断、effect replay、网络失败恢复；测试数量本身不是可靠性指标。

视觉改进应服务以上行为：明确保存中/失败/成功、保留上下文、错误可恢复、键盘路径完整。现有中性主题、自托管字体、紧凑后台布局可以继续使用。没有实测依据时，不建议凭硬编码颜色数量或控件尺寸就宣布对比度/触摸标准不合格。

## 架构补充：是否保留 Astro

**手写静态生成完全可以达到同等级访问性能；当前建议保留 Astro，先测量可选客户端功能。** 这是基于当前实现的工程判断，并非 Astro 必然比手写快。

当前 `apps/web/astro.config.ts:7` 明确 `output: 'static'`。Astro 将模板预生成 HTML，访问者不需要等待 Astro 服务端渲染；静态输出本身并不要求携带完整前端框架运行时。[Astro 官方渲染说明](https://docs.astro.build/en/guides/on-demand-rendering/)也明确构建期预渲染模式。

但本项目不是“零 Astro 客户端代码”：`apps/web/src/layouts/BaseLayout.astro` 使用 `ClientRouter`，多个模块监听 Astro 导航生命周期。去掉这部分可选功能与去掉整个 Astro 是不同工作，性能收益需要分别测量。

真正决定浏览器性能的是 HTML/DOM 规模、下载与执行的 JS、CSS、图片字节与尺寸、缓存命中和请求时序。若手写生成器输出等价产物并使用相同缓存策略，浏览器性能可以相当；若同时减少无用 JS/请求，也可能更快。没有对照实验，不能承诺百分比收益。

移除 Astro 需要接手的现有职责包括：

- `.astro` 模板、布局和输出转义，三种语言页面与静态 JSON 路由生成。
- `astro:assets` 的 `Image` / `getImage`、字体资源，以及现有 assets pipeline 集成；图片优化能力见 [Astro 图片文档](https://docs.astro.build/en/guides/images/)。
- 构建资源指纹、打包、开发预览、类型检查，以及 ClientRouter 相关导航/清理行为。可继续用 Vite、Sharp 等成熟工具，不必从零实现，但仍需要维护胶合代码和回归用例。

本次主要高优先级问题在 D1/R2 与发布协议，更换 Astro 不会自动解决。现阶段最小路线是保留静态模板编译器，优化最终产物；若主要痛点变成构建耗时或升级维护成本，再做单页面手写生成原型，比较同数据、同图片、同功能、同缓存下的性能和维护成本。

历史 `docs/benchmarks/2026-04-08-react-removal-benchmark.md` 记录的是移除前台 React 的对照，不是去除 Astro 的对照，且包含开发环境指标，不能用来预测本次迁移收益。
